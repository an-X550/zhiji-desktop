# 桌面端 UI 审查与设计方案

日期：2026-09-08。状态：待执行方案，未修改产品代码。

## 结论与证据边界

建议把知己收敛为**安静、清晰、有温度的中文写作工作台**。优先重排空间与操作层级，保留深绿作为少量强调。苹果设计只是参考，不是验收目标。

本轮为节省成本的单上下文定向审查，参考本地 impeccable 的 Operate/Read 原则，不是完整双 Agent critique，也没有自动评分。读取当前 renderer、CSS、导航、弹窗和测试入口；使用现存 `out/知己-win32-x64/resources/app.asar` 启动隔离空数据实例，浏览开始、日志、Agent、复盘、设置五页。未使用真实日志、密钥或真实模型。最终截图关闭页面入场动画，避免误把动画中的低透明度当成对比度缺陷。

截图视口为 1186×718 CSS px，图像为 1483×898 像素；保存在 [截图目录](ui-audit-2026-09-08/)。打包版显示 2.6.8，包内 CSS 的深绿、Agent 最小高度、字阶及设置标签与源码抽样一致；未证明整个打包版与当前工作树逐文件一致。因此视觉证据是本地打包版参考，源码结论以当前文件为准。历史长列表、长对话、暗色和最小窗口尚未运行验证，不宣称已全面验收。

## 第一性原理判断

真实问题不是“不像苹果”，而是控件、容器和说明占据主要注意力，写作与阅读反而退居其次。

- 已知事实：主流程是记录 → 反馈 → 行动验证；Windows Electron + React；本地数据和受控 AI；已有设计变量、共享组件、暗色和减少动效支持。
- 待验证假设：减少表单前置步骤、提高正文空间占比，会比更换配色更明显地改善使用感；“丑”的反馈来自一位同学，不能据此推断所有人的偏好。
- 约束：保留现有保存、未保存离开确认、取消、预览 token、审批 ID、备份恢复及数据权限；不因视觉改造增加真实模型调用。
- 取舍：用克制的工作台风格获得耐看和效率，接受它没有营销网站那样强烈的第一眼戏剧效果。
- 最小验证：先做日志与 Agent 两个高频界面，在相同窗口、主题、内容下看前后截图并走通主操作；通过后推广，不同时探索三个风格。

## 推荐视觉规格

下面是首轮实现起点，不是未经测试的客观最优值。

| 项目 | 规格 |
|---|---|
| 整体 | 平整的工作区、紧凑导航、清晰正文。避免玻璃叠层、装饰渐变、仪表盘统计墙、模拟 macOS 红黄绿窗口按钮。保留 Windows 原生窗口行为。 |
| 布局 | 导航宽约 208px；紧凑宽度约 168px并保留文字；工作区边距 24–32px。顶栏与页面标题整合，主标题通常 22–24px；保留 heading 语义。 |
| 明色 | 工作底 `#F6F7F6`，正文面 `#FFFFFF`，主字 `#202622`，次字 `#59645E`，分隔线 `#DCE2DE`，强调沿用 `#0D7A5F`。白底输入边界用更深的独立 control-border token，不能直接拿淡分隔线代替必要控件边界。 |
| 暗色 | 底 `#171B19`，正文面 `#202622`，主字 `#EDF2EE`，次字 `#ADB8B0`，强调 `#79C9AA`，强调按钮文字用深色。所有值需对比度实测，不能把浅色 hex 散落组件。 |
| 字体 | 保留 Windows 系统中文字体回退，不下载 SF/大中文字体。界面 14px、正文 16px/1.75，元信息 12–13px；中文正文约 36–44em、最大约 720px，按实际汉字行长微调。 |
| 间距与形状 | 4/8/12/16/24/32px；按钮与输入圆角 8px，必要面板 12px；普通内容不带投影。列表用行、分隔线和选中底色建立层级。 |
| 控件 | 常规高度 36–40px，图标按钮至少 32px；一处主流程一个实心主按钮，次要动作用中性描边/文字，绿色不覆盖所有辅助按钮。 |
| 动效 | hover/focus 约 120–180ms；去除整页上移、卡片上浮和全按钮 scale。loading/状态动效保留减少动效适配。 |

### 按页面落实

1. **日志**：页头“日志”与写作/历史切换；正文上方一行日期、项目、模板入口，展开编辑仍可到达；大面积无嵌套阴影的编辑区；底部操作条含保存状态、仅保存/生成反馈。不可伪造自动保存。反馈在编辑器之后形成独立阅读段落。统计移到正文之后的轻量文本区。窄窗口元信息换行，不能压缩正文到无法阅读。
2. **Agent**：全局导航 → 会话列表 → 对话；会话列表 200–220px，无外层阴影。紧凑窗口折叠会话列表为可展开入口。对话头只放标题和必要状态；模型详情与历史工具活动可折叠；审批卡保持显著、不得藏入默认折叠区。消息正文主导，输入区固定在该面板底部，流式内容不能无条件把正在读旧消息的用户拖回底部。空态标题、示例、按钮用 12–24px 间距组成一个紧凑组。
3. **复盘**：保留生成/历史和更多洞察；周/月/项目改为紧凑类型选择，下面只有一个配置区域。过程按“范围 → 预览材料 → 确认生成 → 结果”依次展示，保留原 token 和确认调用。
4. **记录/项目**：保留主从浏览；列表使用日期、短标题、摘要，选中状态明确。阅读区不套第二层卡；项目统计变成一行，重命名/归档等次级操作降级，但保持可发现。项目详情现有“最近活动”重复展示只留一处。
5. **设置**：保留通用/AI 与个性化/数据与隐私。每组是标题加设置行，复杂内容才使用展开区；所有删除/迁移确认保留。标签需键盘切换、aria-controls 与 panel 关联。

## 成熟资源与成本决策

| 资源 | 决策与理由 |
|---|---|
| 现有 React + CSS variables + 共享组件 | 主方案，零新增依赖优先。真正问题在组合和布局，迁移 Tailwind/shadcn/整套 UI 框架会扩大改动而不自动提高审美。 |
| [Impeccable](https://github.com/pbakaus/impeccable) | 已有本地 skill，复用 Operate、排版、布局、收敛原则；不用重新安装或同时运行全部命令。设计判断不能用 detector 分数替代。 |
| [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/) | 参考层级和内容优先原则；这是 Apple 平台指南，不照搬材质和平台控件到 Windows。 |
| [Radix Dialog](https://www.radix-ui.com/primitives/docs/components/dialog) | 官方文档包含焦点管理与键盘支持。仅原生 dialog 与现有封装无法满足已验证需求时引入 Dialog，复用现有样式；不为“成熟”安装整套主题。 |

资源检索日期 2026-09-08；没有依赖 stars 推断质量，也未承诺未经验证的版本兼容性。

## 前后端联动范围（按用户补充要求）

用户允许提出并实施支撑前端体验的后端改动。已完成的原子写入、维护协调、IPC 来源校验、MiniSearch 增量缓存、生成重试与取消继续复用；本轮不重新设计它们。界面重排本身不要求改后端，以下按真实需求区分。

### B1：证据按钮准确打开原记录，纳入本轮

源码事实：`agent-page.tsx` 的 `evidenceNavigationTarget(kind)` 只接收类型，没有使用 `hit.id`；日志证据只能进入记录列表，复盘证据只进入复盘页。用户读到一条证据后还要重新找原文，削弱可验证性。

最小方案：点击经过 `AgentEventSchema` 校验的本地证据时，将 kind + id 转为 renderer 的明确“打开记录”导航意图，让日志/复盘历史阅读器选中该记录；复盘来源必须进入历史标签。先复用已加载数据以及现有 journals.get / reviews.get。不要为了 UI 内部跳转扩大模型可调用导航 schema；只有确有共享契约消费者需要时才做兼容增量扩展。记录删除/不可读时明确提示，不静默打开第一条。保留来源校验和未保存离开确认，不把路径或 URL 当成记录 ID。

这项通常可仅改前端；若详情读取缺少可区分的 not-found 错误，在既有共享错误/IPC 中最小补齐即可。无需新增搜索服务。

### B2：列表传输与渲染按实测决定是否联动

源码事实：`hooks/use-app-data.ts` 每次 refresh 同时读取全部日志、项目、复盘、配置和目录信息；`history-page.tsx` 对完整正文做前端筛选并渲染全部命中；`agent.list()` 返回 `AgentSession[]`（包含 messages），已有 `agent.get`。单会话 schema 上限 200 条消息，不等于整个会话列表传输已轻量化。

这些是规模风险，不是已测得的性能故障。已有 MiniSearch 优化面向检索，并不证明首屏 IPC 传输或 React 渲染没有瓶颈。

先用 100/1,000 条合成记录和 20 个含消息的会话，记录冷/热加载、IPC 数据量、搜索到下一帧、列表滚动；慢路径再扩到 5,000 条，不默认做大型基准工程。先按渲染瓶颈使用前端分页/延迟筛选/局部刷新。若 IPC/读取占主导，再增加只读摘要查询（id、类型、日期、标题、短摘要、项目 ID）和按需详情；Agent 优先 summary list + 现有 get，事件仍可兼容现有格式。

跨层扩展前明确查询语义：全文搜索在后端针对完整语料，不能只搜当前页摘要；稳定排序及唯一 ID 次排序，游标失效可重载；统计与 `resolveNextStep` 不得只消费当前页导致错误；数据根切换失效复用现有协调机制。新接口走原 IPC 包装与 Zod 校验，不迁数据库，不建立第二份权威数据。

若采用摘要接口，首轮保留旧 list 给未迁移消费者，UI 的列表/详情链路实际迁移后再谈收益，不能仅新增一个没人调用的接口。是否撤旧接口另按消费者证据决定。

### B3：真实生成状态复用，先核查恢复缺口

现有 `reviews.onTaskPhase` 和 Agent 事件已足以显示“整理材料/生成/保存”等阶段；只改前端呈现，不制造百分比或 ETA。审批卡/工具活动目前存在 AgentPage 的局部 state，页面卸载后能否恢复尚未实测。

执行时测试：运行中离页再返回、等待审批时离页再返回。如果状态会丢，优先将订阅与临时 UI 状态提升至应用级以覆盖页面切换。只有 Main 持有状态但 renderer 无法重新获取时，才增只读状态快照；复用现有 task/session/approval ID，并同步校验过期。禁止重新生成 approvalId、重放写操作或把失联状态显示为成功。不将该修复扩展为跨进程持久任务系统。
