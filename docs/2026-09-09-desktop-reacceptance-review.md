# 桌面端二次验收：结论与修正方案

日期：2026-09-09。结论：**部分通过，整体不能验收通过**。功能通路基本可用，但布局未完成、重新生成语义错误，且反馈内容有证据越界。本版按用户最新要求替代上一轮“同日多份日志综合分析”的设计，不修改此前验收记录的历史事实。

## 2. 第一性原理判断

用户要的是“把这一天的记录写完整，然后获得针对这份记录的反馈”。前案为了兼容技术上的多记录结构，保留了“另记一条并汇总”，现在已与用户明确意图不符，应纠正，不能用已有代码反过来定义用户需求。

布局的目标是让用户把注意力放在正文，而不是把页面撑得很长。字号增大、留白增大、加了卡片，都不等于阅读体验改善。固定位置的“日志 / 日分析”切换适合这里：这两项占用同一块主要空间，减少无意义的上下滚动，比在窄屏左右分栏更简单。

## 3. 问题、证据与方案

### R1：正文高度仍不足，原验收夸大了完成程度

`src/index.css:363–364` 仍是 textarea min-height 190px、resize vertical、overflow-y auto；today-page 没有根据正文或剩余视口分配高度。实测逻辑视口 1186×718，644 字合成正文：编辑器可视高度 212px，内容高度 417px。截图也显示明显内滚。

修正：日志工作区占据主视口；压缩日期区、项目/模板工具区，已有日志提醒改成一行状态而非大色块。顶部工具和底部保存栏不增长，正文区域获得剩余高度。长文仅编辑区域滚动，外壳不再与它同时滚动；窄/极低高度时允许必要退化，不强求任何长文一屏放完。不要继续仅增加 min-height 或要求用户拖 textarea 手柄。

验收用比例和任务：正常桌面窗口正文可视高度应至少约占主内容可用高度一半；这些比例只作初始参考，不设脱离实际视口的硬性像素指标。关键是明显多于当前小框、操作不遮字，不能为凑数字制造横向溢出。

### R2：整体放大与局部字号是两个问题

用户应用的 Preferences 对当前 packaged file 页面保存了 zoom level 1.223901…，对应约 125% 页面缩放；系统显示缩放实测 125%。隔离新 userData 下 Electron zoom 为 1，CSS 全局正文为 14px，编辑区 17px。**不能断言所有 CSS 字号被调大，也不能确认保存的缩放是用户操作还是上次测试留下。**

另有明确局部变化：`.daily-feedback-panel__content .markdown-document` 覆盖为 17px，而通用 Markdown 正文为 15px。上一轮把“更大”当改进并不符合本用户偏好。

修正：先记录用户实际运行页的 zoomFactor，在隔离测试窗口以 100% 和用户当前缩放分别复看，不改 Windows 缩放、不删除整个 Preferences、不每次启动强制重置用户选择。测试必须隔离 userData。日分析恢复与原普通阅读区一致的 15px；导航、按钮保持既有字阶，编辑器优先恢复原使用基准而非再加大。无须新做字号设置面板。

### R3：明确重新生成命中了缓存

`DailyFeedbackPanel` 只回调日期；`today-page.tsx` 统一传 `{date}`，未携带 `regenerate:true`。`GenerateDailyReview` 对未变来源直接返回旧记录。因此按钮称“重新生成”却没有发请求，实测已确认。

修正：查看/复用缓存与“重新生成”是两种不同意图。前者不花钱并显示“已显示已有反馈”；后者传强制参数，实际调用并成功覆盖。保存新正文后使用对应 sourceVersion，不能只刷新成功横幅。无需通过比较两次输出文本是否不同来判断是否调用，模型也可能合法返回相近内容。

本次修改原文后真实生成成功，故不能把所有日分析都称为假功能。用户“新输入后内容仍旧”的具体界面路径还需回归，重点核对保存目标 ID、请求快照、缓存和 UI override，不能只修强制参数就宣布所有情形解决。

### R4：按当前日志分析，停止自动汇总同日多条

默认打开今日（历史日期同理）已有唯一日志直接继续编辑，日期旁显示“正在编辑已保存日志”。无记录才新建。保存更新原 ID；再次写入是在这一份记录上修改/追加，不由系统默默拼接两份材料。

用户已写草稿才切到有记录的日期时，保留草稿并明确“该日已有日志”；用现有未保存守卫先处理草稿，再打开原日志。不能丢草稿、自动替换已有记录，也不保留“另记一条并汇总”作为推荐路径。

旧数据同日多条：保留原文，在日期列表选择需要继续编辑的一条；不自动选最后一条、不自动合并/删除。日分析只取明确选中的 journalId 的最新已保存正文。日期只决定反馈归属日，不决定输入集合。前次反馈如继续用于行动对照，必须标日期为历史上下文，不混作本次日志证据。

日反馈仍每天一份。由另一条历史记录生成时可以成功替换，但应明确来源是那一条；打开未作为该日反馈来源的旧记录时，显示“本日反馈来自另一条记录”及查看来源入口，不能把它标成当前条“已更新”。新鲜度比较仅针对实际 sourceIds/sourceVersions，不再与所有同日日志比较。

### R5：做切换，不把两篇长文叠加

在当前写作面和历史详情顶部放“日志 | 日分析”切换，两者共用同一内容区域。只显示选中的一面，不做左右同时展开的双栏，也不在底部重复全文。

默认日志；生成成功且用户未离开该记录/继续修改时可切日分析，否则只提示完成。切换不丢草稿、不自动发 API，返回日志保留光标/滚动位置。日分析可独立滚动，已有结果随时可读。

`today-page.tsx` 与 `HistoryReader` 当前确实把 panel 追加在正文后；原计划已有切换意图，但实际未实现。用户第三张截图存在阅读内容与反馈日期疑似不一致，当前源码虽有 date 过滤，仍不能仅凭源码断言截图原因；本轮未复现该错配，列为跨日期回归必测，不擅自改用户历史日期。

### R6：日分析冗长且有证据越界

`renderDailyReview` 重复写 action.step（“明天试试”与“新认知”中各一次），外部日期标题又与正文标题重复。保留独立 Markdown 的日期标题，只收敛外层重复标题；先去掉重复行动，不为压短正文额外调用 AI。保留一个洞察、一个动作、必要的上次行动对照；前次反馈未必是昨天，“昨天你答应自己”应改为有日期的“上次反馈建议”，不能把 AI 建议当用户承诺。

本轮真实输出从“未记录校对标准”推到“方法缺乏结构”，周/月报进一步写成“未设置检查清单”“根因是方法未结构化”。原文没有这些证据。模型能返回 JSON 只代表协议成功，不能判定分析合格。

最小修正：提示词增加明确反例“未提到清单 ≠ 没有清单，未记录方法 ≠ 方法无效”；周/月消费日反馈时不能把推测升格事实。允许只给有依据的反馈，不为强行找盲点制造问题。保持现有大体 schema，暂不引入评分模型或多次模型审核。普通日反馈以已有 260 字目标为参考，阅读区容纳合理长例外；不因超一点字数就自动多花一次请求。

### R7：Agent 消息空间被重复标题与常驻辅助区挤占

用户补充截图直接支持此问题，不需要新增模型调用来验证布局。源码 `agent-page.tsx` 同时有页面标题/说明、会话标题/状态/模型信息；`index.css:557` 起还有 page-hero 留白、固定 208px 会话列、conversation header 和 rows=3 输入区。外壳另有“知己 Agent”顶栏，重复展示同一身份。消息区虽已 flex:1，但只能拿到这些组件剩下的空间，单独再写 flex:1 不会解决。

方案：保留一条紧凑会话工具栏（当前会话、新建、会话列表开关）；删除重复的 Agent 大标题和运行边界说明，模型状态压成一行次级文字/现有设置入口。“删除会话”放现有次级操作区域，不作为大红按钮长期抢占头部。桌面会话列表可折叠，默认紧凑；窄窗口沿用已有折叠逻辑，不新增复杂抽屉框架。保留全局导航，不为节省空间隐藏所有入口。

消息区获得主要剩余高度、独立滚动；输入框初始 1–2 行，随输入适度增长到上限再内部滚动。正常阅读态消息区域目标约占 Agent 主工作区高度的 60% 以上，极小窗口/待审批状态另按可达性检查；不通过缩小字号凑比例。消息正文仍保持适当阅读行宽，不把超宽屏每行拉满。用户上翻时新消息不强制拉回底部。

工具已完成状态和证据默认紧凑、可展开；待确认审批、运行中停止和错误不得被折叠隐藏。只改 renderer 与必要共享布局，不碰 Agent 调度/模型协议。本轮已通过的 Agent 读工具不再重复付费测试，布局用合成会话与离线事件验证。

### R8：浅色主题失去层次，优先恢复旧版已有做法

源码明确：`.review-type-card { background: transparent }` 覆盖了 `.card` 的白色 surface；背景本来已是很浅的灰，边线又浅，导致用户截图中的卡片融入页面。当前 sidebar 删除了右侧边线。对比 Git HEAD 旧版：review-type-card 没有透明覆盖，继承 card surface；sidebar 有 border-right。HEAD 只是可核查参考，不声称是用户记忆中那一版安装包。

方案：复盘卡片恢复独立 surface 背景，侧栏恢复分界线，保留背景/侧栏/内容的层级；先复用旧实现与现有 tokens，不更换配色体系。次级按钮使用明确填充或边框，与卡片正文区分，主按钮保留强调色。选中导航有稳定底色和文字强调，hover/focus 可分辨。边框按控件和分区作用调整，不能为了“更清楚”给所有内容套厚框或巨大阴影。

跨页面只检查受共享 tokens 影响的日志、Agent、复盘、设置明暗主题，避免浅色修复破坏暗色。通过实际截图和文字/控件对比度测量确认，不凭颜色值看起来深一点就宣布可用。复盘已有卡片可以继续使用，不新增仪表盘或重排信息架构。

## 4. 范围与完成标准

本次必修 R1–R8；Agent 增加上述消息空间修正，浅色主题只做有证据的层次修正。周/月/Agent 后端只修证据直接支持的内容质量或契约传播问题，不重做功能。旧方案中“同日所有日志作为日反馈输入”“另记后综合分析”停止执行，原始多份数据保留兼容。保持原子写、单日反馈覆盖、previewToken/approvalId 等安全边界。

完成要能真实走通：一天再输入时编辑原记录 → 保存 → 请求只包含当前正文 → 得到基于新正文的反馈；明确重新生成有请求；标签切换减少滚动；正常缩放下恢复原字号密度。测试数字不能替代这些行为证据。

## 5. 最终可行性复核（细化并修正上文简写）

以下是同一方案的实施边界，不新增产品功能：

- **日期导航与改日期分开**：主日期选择表示打开某天，不得把正在编辑的日志移到那天。已有草稿时取消就保留原日期原文，用户可先保存再切换；不要先切日期再问。旧的更正归属日能力保留为明确的次级操作，不另建移动系统。
- **自动载入只在合适时机**：首次进入且没有草稿才加载当天唯一记录；后台刷新、切回页面、跨午夜不能重置编辑内容。旧同日多条仍由用户选，不新建“主日志”索引或强行合并。
- **单条指当前材料，不是整个提示词**：当天原始日志输入只有选中条的新正文。已有获准使用的个人背景、前次反馈可以保留，但必须单独标为背景，不能混作当天证据。保存 sourceVersions 和判定新鲜度必须对应实际日志。
- **保留导出可读性**：落盘 Markdown 保留日期标题，外层不再重复大标题；删除重复行动，不裁切或重写用户旧反馈。前次反馈日期从实际 previousReview 上下文传到渲染器，不能让模型编日期。
- **质量约束与标题一致**：保留 insight 字段即可，但固定“你没注意到的”改成中性“本次观察”，允许有依据的镜像，不强制找盲点。周/月引用原因时核对原日志，不能仅靠日反馈推测。少量验证改善不等于模型永不出错。
- **空间目标看实际增益**：对比同视口、同缩放下修复前后正文/消息高度和可见行数。像素与百分比只作参考；长文正常滚动，超小窗口以操作可达优先。Agent 原本在底部时跟随新消息，上翻时不强拉底；不能一律停止自动滚动。宽窗口会话列表可展开并保留本次选择，窄窗口默认收起。
- **真正验收再输入**：最终用同一条短合成日志，在真实编辑界面输入 A 保存生成，再改成 B 保存生成。确认两次发送材料和版本、反馈 ID、界面内容；不能再次只调用 IPC 后声称整个输入流程通过。强制重生成/空白/并发等用离线请求计数，避免额外费用。

可行性判断：R1/R5/R7/R8 是现有 React/CSS 局部调整，R3 复用已有 regenerate 参数；R4 的日分析调用方适配是主要复杂度，必须覆盖 IPC 和 Agent，不能当纯前端改动。已有 sourceIds/sourceVersions 足以表达单条来源，无须数据库或额外记录系统。先修数据与请求语义，再布局和内容质量，最后按真实用户流程验收。设计依据是用户描述与本轮证据，不冒充已做用户访谈。
