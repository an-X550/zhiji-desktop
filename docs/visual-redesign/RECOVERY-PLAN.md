# 修复执行规划

依据：[审查与方案](RECOVERY-REVIEW.md)。目标目录为用户指定的 `apps/zhiji-desktop`。不切换仓库，不整仓回退，不混入已有修改。

## 阶段一：复现并修复 AI

1. 读取当前版本、适用规范、provider/runtime/application/IPC 的相关实现与既有测试。核对实际运行包来源；服务商、模型及请求参数仅记录脱敏元数据。
2. 先以合成有效日志验证 create/update → 保存完成 → 按日期读取 → buildDailyContext → provider 请求全过程，断言提交正文确实进入请求；不要只mock生成按钮或将编辑器清空误认为输入为空。再用现有 provider 集成测试的模拟服务器复现：空正文＋length、非空截断、正常 JSON、无 length 空正文、schema 错误。验证当前请求上限与第二次请求无变化的问题。
3. 按实际服务商能力修正预算、诊断分类和一次有区别的重试；复用现有类型／工具，不新建 AI 框架。补测第二次实际参数变化、两次总上限、取消与认证不误重试、失败不落盘、成功只保存一次。
4. 打通周期错误显示，去掉 IPC 包装，保留材料与已有预览确认机制。错误返回类型若变化，同步 preload/schema/caller 测试。
5. 经用户已授权的服务商和材料范围进行最小真实验证。若没有授权上传任何材料，先完成模拟集成和合成材料准备，再明确请求一次仅发送合成材料的验证授权；不得擅自用用户日志。已有同范围授权则不重复询问。

真实验证最小集合为短日反馈和月复盘，记录有效正文、schema 通过和落盘结果。周／项目复盘与 Agent 先用现有模拟测试覆盖不同路由；只有发现独有问题才扩展真实调用，避免花费与重复上传。对真实模型未验证的功能明确标注覆盖范围。

## 阶段二：局部恢复界面

1. 从提交 `458f5d7` 提取首页局部样式和必要依赖，恢复旧卡片布局及文字比例；适配当前明暗变量，不整体恢复旧 CSS。用户第一张截图为参考。
2. app-shell.tsx 复用品牌副标题，采用“记录，分析，行动”；顶栏恢复页面名称。
3. today-page.tsx 删除写作区最近记录与本周摘要，保留历史入口和本次反馈；删除对应无用派生值。
4. 正文、工具、状态、footer 共用宽度与内边距。保存后保留内容，复用 saved journal 身份与 dirty 判断，防止重复保存和误报未保存。

## 阶段三：一次集中验收

- 首页：明／暗、恢复窗口／最大化，对照旧截图的卡片分组、字号与位置。
- 写作：空正文、短文、长文，正文与操作同列；去掉无关列表后不过度拉高编辑器；紧凑窗口保存动作可达。
- 保存：create 后保留已保存正文，编辑后 update，再次点击不创建重复记录；切换页的未保存守卫正确；AI 失败后仍能查看原文、重试成功。
- AI：日／周／月／项目复盘及 Agent 的路由覆盖表；每项写明模拟还是真实。失败不覆盖旧报告、不泄露 Key／正文；实际有效报告可读取。
- 共享样式：历史页无重叠、原生下拉暗色可读、Agent 输入框与发送按钮可达。

复用现有 typecheck/lint/相关单测与 integration/E2E；涉及 provider 与保存逻辑后运行已有完整测试，再 package 当前产物做上述页面检查。修复发现的必要缺陷，确认通过后停止额外视觉打磨。
